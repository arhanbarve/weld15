# P0 — Scaffold, tokens, data, test harness

Prerequisite phase. No 3D of substance, no geometry logic. The point is that every later phase has
a build that compiles, a test runner that runs, and a design system already wired, so no phase has
to stop and do setup.

---

## Objective

A Next.js app that builds clean, renders one cube in the locked cyanotype palette, serves the
Harvard GIS data from inside `src/`, and has both test runners working against real assertions.

**Done when:** `npx tsc --noEmit`, `npm run build`, `npm test`, and `npm run test:e2e` all pass, and
a Chrome screenshot shows the cube in the right colours with the right fonts.

---

## Version scrutiny — checked against the registry, not assumed

The plan document said Next 15. It is wrong; Next is at 16. Two real traps turned up.

| Package | Pinned | Why this exact choice |
|---|---|---|
| `next` | `16.2.12` | Current. Engines `node >=20.9`; local Node is 26. Peer accepts React `^19.0.0`. |
| `react` / `react-dom` | `~19.2.8` | **The important pin.** `@react-three/fiber@9.6.1` declares `react: >=19 <19.3`. A float to React 19.3 silently breaks the renderer. Tilde holds the 19.2 line. |
| `three` | `^0.185.1` | R3F wants `>=0.156`, drei `>=0.159`. Satisfied. |
| `@react-three/fiber` | `^9.6.1` | v8 does **not** support React 19. v9 is required, and it is what sets the React ceiling above. |
| `@react-three/drei` | `^10.7.7` | Requires `@react-three/fiber: ^9.0.0`. Supplies `Line2`, needed in P3 because GL line width is capped at 1px and the accessibility gate demands ≥1.5px. |
| `zustand` | `^5.0.14` | Store. No provider needed, works outside React for the animation loop. |
| `three-stdlib` | `^2.36.1` | `BufferGeometryUtils.mergeGeometries` for the campus merge in P3. |
| `typescript` | `5.9.3` | **Deliberately not 7.0.2.** TS 7 is the native port and is `latest`, but `@types/three`, vitest and the eslint plugins are the risk surface, and there is nothing in this project TS 7 buys. Revisit after P8. |
| `vitest` | `^4.1.10` | Geometry tests in a Node environment. No jsdom needed; nothing under test touches the DOM. |
| `@playwright/test` | `^1.62.0` | Next 16 lists it as a peer at `^1.51.1`. Satisfied. |

Two traps, written down so they do not recur:

1. **React ceiling.** R3F 9 caps React below 19.3 while Next 16 does not. Only the tilde pin
   prevents a future `npm install` from breaking the canvas. Verified in P0 by asserting the
   installed React version in a test.
2. **TypeScript major.** `npm install typescript` would fetch 7.0.2 today. Pinned to 5.9.3.

### The P0 test is not a placeholder

`tests/data.test.ts` asserts things that would actually break the project if wrong, and it doubles
as proof the data survived the move:

- `campus.json` has 39 buildings, every one with a `height_ft > 0` and a ring of ≥ 5 points
- Weld Hall is present in `campus.json` with `height_ft === 87.01`
- `weld.json` ring 0 has 59 points and is closed — first point equals last
- Weld's bounding box is 82.9 × 150.9 ft ± 0.5, which is the 54 × 151 building rotated 13.2°
- the installed React major.minor is `19.2` — the ceiling trap, asserted rather than remembered
- every ring is wound consistently, checked by signed area, so extrusion in P1 cannot flip normals

## Step sequence

1. `npm init` the Next app in place. The directory is not empty, so scaffold manually rather than
   fighting `create-next-app`, which refuses non-empty targets.
2. Write `package.json` with the pinned table above. `npm install`.
3. `tsconfig.json`, `next.config.ts`, `vitest.config.ts`, `playwright.config.ts`.
4. `app/globals.css` from MASTER.md. Both themes, both stage palettes, z-index scale, focus ring,
   reduced-motion block.
5. `app/layout.tsx` with the two fonts self-hosted.
6. Move the data, add `tests/data.test.ts`, run it. **Data test must pass before any 3D goes in** —
   if the geometry is wrong, everything downstream is wrong.
7. `src/scene/Experience.tsx` and `app/page.tsx`.
8. `npx playwright install chromium`, add the smoke spec.
9. Run the full verification set.
10. Screenshot the dev server in Chrome.
11. **Ask before `git init` and the first commit.** Not doing this unprompted.

## Failure modes anticipated

| If this happens | Then |
|---|---|
| `create-next-app` refuses the non-empty directory | Scaffold by hand. Already the plan. |
| React resolves above 19.2 and the canvas throws | The tilde pin plus the version assertion in `data.test.ts` catch it at test time, not at runtime. |
| `resolveJsonModule` blows up the bundle by inlining 34 KB of JSON | Acceptable at this size. If it becomes a problem in P3, switch to a `fetch` from `public/`. Noted, not pre-optimised. |
| Fonts fail to fetch at build | `next/font` fails the build loudly rather than silently falling back, which is the behaviour I want. |
| Playwright cannot boot the dev server in CI-less local runs | `webServer.reuseExistingServer: true` so a running dev server is reused. |
| Turbopack chokes on `three` | Fall back to webpack via `next build --no-turbopack`. Unlikely; three is pure ESM/CJS with no native deps. |

## What actually happened

All four gates pass. Four things turned up that the plan did not predict.

### 1. Three degenerate rings in the campus data — caught by the test, not by eye

`data.test.ts` failed on its first run: a Smith Campus Center ring enclosing **0.045 sq ft**. The
distribution has a clean gap — three rings at 0.045, 1.0 and 4.7 sq ft, then the next smallest real
ring at 802 sq ft. All three removed with a 50 sq ft floor, so `campus.json` now holds **36
buildings, not 39**. Extruding a sliver produces degenerate triangles, so this would have surfaced
in P3 as garbage geometry with no obvious cause.

### 2. Mixed ring winding — would have rendered four buildings inside-out

Checked the data before writing the assertion, which is the only reason the assertion is right: 35
rings clockwise, 1 counter-clockwise after cleaning. **`extrude.ts` in P1 must normalise winding
before generating side quads**, or the odd building out gets inverted normals and renders black. The
test asserts both windings are present, so if the data is ever refetched clean the test fails and
tells us the normaliser stopped being load-bearing.

### 3. `ssr: false` is illegal in a Server Component under the App Router

`next build` rejected `next/dynamic({ ssr: false })` in `app/page.tsx`. Required a client wrapper,
`src/scene/CanvasHost.tsx`, whose only reason to exist is holding that boundary. It also carries the
loading fallback, which reserves the full viewport so the canvas mount causes no layout shift.

### 4. Two wrong diagnoses of a blank canvas, recorded so they are not repeated

The scene looked blank in the extension-controlled Chrome tab. I twice concluded wrongly:

- **First guess: the camera was not aimed at the origin.** Wrong. `OrbitControls.update()` calls
  `lookAt(target)` on its first frame, so the camera was always aimed correctly. Measuring both
  states with `scripts/measure-render.mjs` returned identical metrics, which is what disproved it.
  The `onCreated` `lookAt` was kept anyway — deterministic initial orientation before controls mount
  is worth having — but it repaired nothing and is not described as a fix.
- **Second guess: a screenshot-timing race.** Also wrong. The real cause is that the tab is not the
  frontmost window, so `requestAnimationFrame` is throttled after the first frame. One frame drew
  the clear colour before children mounted, then the loop paused. My earlier drag delivered an input
  event, forced a repaint, and the cube appeared. Headless Chrome, which is never occluded, renders
  it correctly every time.

**The lesson that changed the code:** the original e2e test asserted a WebGL context existed, which
a completely broken scene satisfies. Its replacement counted non-background pixels, which the
40-unit grid helper satisfies on its own — it passed with the cube deleted. The version that ships
uses a luminance threshold picked from measurement: background ~101, grid lines ~158, lit cube faces
420-580, so requiring pixels above 300 isolates the cube. Verified in both directions — 5.3% with
the cube, **0.0% and a failing assertion with the cube removed**. A test that has never been seen to
fail is not evidence.

`scripts/measure-render.mjs` was written for that threshold-picking and stays in the repo; P3 and P5
need the same measured-not-guessed approach for their visual gates.

### Advisory assessment, not silenced

`npm audit` reports 3 high findings, all transitive under `next`: `postcss` (3 advisories) and
`sharp` (libvips CVEs). The only remediation npm offers is `next@9.3.3`, a 2020 release — npm found
no forward path because the fix lands in `16.3.0`, still in preview, and `16.2.12` is the newest
stable. Both packages are build-time only here: `postcss` processes CSS we author ourselves, and
`sharp` is an optional image-optimisation dep this project never invokes. **Not downgrading. Not
running `audit fix --force`,** which would break the React pin. Re-check when 16.3 goes stable.
