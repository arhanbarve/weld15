# P7 + P8 — walk it, then ship it

## P7 — first person and mobile

### Goal

Stand in the suite at eye height and walk it. Hand someone a phone and have it hold up.

### Why first person also fixes a debt

`stages.ts` carries a comment recording that the stage 4 → 5 camera path flies **through** the
partition between bedroom B and the hall, and at t = 0.7 landed half a foot from that wall — the
near plane — so every face clipped and the frame went empty. The workaround was to stay inside
bedroom B. Routing a path through the doorway needs a spline and collision, which is exactly what
first person builds. So P7 pays that back: once the walker exists, the threshold can land in the
hall, which was always the better shot.

### Contracts

```ts
// src/geo/walk.ts -- pure, no three.js
export const EYE = 5 + 10 / 12;      // 5 ft 10 in, already used by stages.ts
export const RADIUS = 0.75;          // shoulder half-width as a capsule
/** Slide along walls rather than stopping dead. Returns the resolved position. */
export function step(from: Vec2, to: Vec2, ctx: { walls: Wall[]; openings: Opening[] }): Vec2;
export function canPass(opening: Opening): boolean;   // doorway clearance vs RADIUS
```

```ts
// src/geo/route.ts -- pure
/** A walkable path between two rooms, through doorways, as waypoints. */
export function route(from: string, to: string, suite: Suite): Vec2[] | null;
```

`route()` is a graph search over `unreachableRooms()`'s adjacency, not a straight line. It returns
`null` when no doorway chain exists, which is the case `unreachableRooms()` exists to detect.

The capsule must not pass through a 0.5 ft partition at any step size. Test it at a deliberately
absurd step — a single frame of 40 ft/s at 5 fps is 8 ft, far more than a wall is thick — because
sweeping a point against a thin wall is the classic tunnelling bug and it only shows up on a slow
frame.

### Mobile

Touch orbit, a shortened intro, first person hidden (no pointer lock on touch), shadow map at 1024,
line widths reduced, DPR capped at 2. The HUD and panel are responsive at 375 / 768 / 1024 / 1440.

### Verification

`walk.spec.ts`: walk the hall end to end and assert the camera never leaves the suite footprint per
`collide.ts`; walk into every wall in turn and assert the position resolves to outside it; assert
the doorway is passable and a 0.5 ft gap is not.

`responsive.spec.ts` at all four widths: no horizontal scroll on `document.body`, every touch
target ≥ 44 × 44 CSS px, the HUD does not cover the viewport's centre.

### `A11yAlt.tsx`

A live region that describes, in prose, what the 3D view is currently showing: the stage, the room
the camera is in, its dimensions, and its provenance. A canvas is opaque to a screen reader, and the
`aria-label` currently on it is one sentence for the whole six-stage journey. The live region is the
non-visual equivalent of the model, and it is also the thing that makes the app usable with the
canvas failing to initialise at all — which is the honest fallback for a WebGL-less client.

Announcements must be throttled. A live region that fires on every frame is worse than none.

### The checklist

**Done. The result is `docs/CHECKLIST.md`** — all sixty boxes of `design-system/MASTER.md`
ticked, each with the measurement it was judged on, taken from a rendered page in Chromium
rather than from the source. **51 PASS · 7 FAIL · 1 N/A · 1 not checked here**, and of the
failures **4 boxes were fixed in `app/globals.css`** (5 rules) with before-and-after numbers;
the rest are handed over with file, element, stage and expected value.

Read `docs/CHECKLIST.md` for the whole thing. The five named items landed like this:

- **Line width ≥ 1.5 px scaled by DPR on dark** — **PASS in Campus, N/A in the exterior.**
  Measured in rendered pixels by walking every scanline and taking each bright run's width at
  half maximum: at DPR 1 the mode is 2 device px with 90.8 % of strokes ≥ 2 px at stage 2, which
  is not the flat 1 px histogram an unscaled `gl.lineWidth` would give; at DPR 2 the mode moves
  to 6–7 and 98.7 % are ≥ 3 px, so the `× devicePixelRatio` term is real. **The exterior draws
  no line work at all** — four solid meshes, no `<Line>`, and `window.__perf.lines` is 122 at
  both stage 2 and stage 3, i.e. Campus's count unchanged by the exterior arriving. So the
  answer to "verify it in P4's exterior too" is that there is no exterior stroke to verify; its
  edges are material and silhouette. Re-take after `WeldExterior.tsx` / `Threshold.tsx` land —
  they were mid-edit and stage 4 read 433 triangles with 0 lines.
- **Colour is never the only indicator** — **PASS, and the cutaway is the strongest case.** All
  four modes driven in the browser and every call site read: the mode's **word** on the button
  face, `aria-checked` true/false inside a `role="radiogroup"` labelled "Cutaway mode", weight
  600 vs 400, a visible hint, a live region, and the `<canvas>`'s own `aria-label` — and every
  string matches `CUTAWAY_WORDS` in `src/scene/cutaway.ts` exactly at all three call sites, so
  `459ebba`'s one-table refactor holds in the output and not only in the imports. Five of the
  six signals are nothing to do with colour. Weld's highlight carries all three MASTER asks
  for, the pulse verified by frame diff (1.6–2.8 % of pixels changing continuously, 0.00 %
  under `reduce`).
- **`prefers-reduced-motion`, with a real alternative** — **PASS, measured in pixels.** Under
  `reduce` a stage change produces **one** frame that changes (by 83.4 % of sampled pixels)
  followed by 24 samples at **0.00 %** — a jump-cut that then holds still. Under no-preference
  the same change is followed by a 20-second tail. Three alternatives, not absences: the camera
  still arrives, CSS transitions collapse to `1e-05s` rather than being removed (the skip link
  still reaches y 14), and Weld's pulse is held at 0.34 rather than dropped. **Not verified:**
  MASTER's specific 120 ms crossfade — screenshotting under SwiftShader costs 400–800 ms here,
  coarser than the interval, and it is not asserted.
- **Contrast ≥ 4.5:1 for body text on both grounds** — **was 1 FAIL in 119, now 0.** Measured
  by hiding each element's own glyphs, screenshotting its text rect and decoding the ground —
  so the translucent chip over the vignette over a live WebGL frame is measured as composited.
  The one failure was `.hud-num`, 11 px of `--mark`, at **4.15:1** against its ground's 95th
  percentile at stage 0, because 18 % of Earth's lit limb comes through `--chip-scan` behind a
  mid-luminance crimson. MASTER's own ledger predicted it. Fixed with an opaque `--void-deep`
  ground: **5.06:1 flat**, both stages, no longer a function of the frame — and axe's
  `color-contrast` incomplete count fell from 14 nodes to 13, the departing node being that one.
- **Focus visible on every control, tab order matching visual order** — **focus PASS, order
  FAIL by one stop.** All **42** distinct tab stops measure `solid 2px rgb(94,166,235)` at 2 px
  offset; not one `outline: none`. Order: 11 of 12 stops at stage 0 walk top-to-bottom, but
  `panel-toggle` sits at y **14**, the topmost control on screen, and is reached **twelfth** —
  after a control at y 661. Mount order in `Experience.tsx`, not CSS, and it has to land third
  rather than first because `a11y.spec.ts` fixes `skip` and `a11y-alt-toggle` in the first two
  places deliberately.

Two findings worth naming here because neither is visible in the DOM, the accessibility tree or
axe — only in the box:

- **The seven-room table in the written description was rendered at zero height**, at all four
  desktop viewports. `.a11y-alt-scroll` measured `clientHeight` **0** against `scrollHeight`
  281, with the first row laid out at y 869.9 outside it. It is the flexbox rule: a flex item
  whose `overflow` is not `visible` has an automatic minimum size of 0, so it was the only child
  of the panel able to absorb the column's shrink deficit and took all 400 px of it while every
  paragraph beside it kept its natural height. `a11y.spec.ts` counted 7 rows and passed; axe
  found nothing. Fixed: `flex: none`, now **301** px with all seven rows inside.
- **`threshold-t` was a 176 × 16 hit target.** `Hud.tsx`'s `TAP` constant predicted this in
  prose — it records that `.hud-t input` sets a width and no height, applies `minHeight: 44`
  inline to the two sun controls, and says it "would sit better as a rule beside `.hud-t
  input`". The threshold slider is the third `.hud-t input`, added later, and never got the
  inline style. The rule is now in `globals.css` where it covers all three.

Still open, in `docs/CHECKLIST.md`'s handover list: `Panel.module.css`'s 1.45 line-height on 26
elements, the `panel-toggle` tab position, no high-contrast toggle anywhere in the app,

### Performance

`axe-core` zero violations on all six stages. Lighthouse ≥ 90 performance, 100 accessibility.
Code-split the globe so it leaves the critical path once you are past stage 0. Audit
`renderer.info` against the budget table in `docs/IMPLEMENTATION-PLAN.md` §9.

Measure frame time on **real hardware**, not headless: every existing perf gate is deliberately on
draw calls and triangles because headless Chromium runs SwiftShader in software, where bloom costs
~70 ms against 1–3 ms on a GPU. P8 is where a real number finally gets recorded, and it has to be
recorded from a real browser on this machine.

### Console warnings, and which of them are ours

A clean console is part of shipping, so here is the accounting rather than a hope.

**Fixed.** `THREE.WebGLShadowMap: PCFSoftShadowMap has been deprecated` fired on every mount, six
times in an e2e run: `Experience.tsx` asked for `shadows="soft"` and three r183 deprecated that map
type. It now asks for `PCFShadowMap`, which is what three was substituting anyway — same rendering,
no warning.

**Not ours, and not fixable from here.** `THREE.Clock: This module has been deprecated. Please use
THREE.Timer instead` comes from `@react-three/fiber`'s own render loop —
`node_modules/@react-three/fiber/dist/events-*.esm.js` constructs a `Clock`, and so does
`three-stdlib`'s `EffectComposer`. Nothing in `src/` constructs one; checked by searching the whole
tree. It goes away when those packages move to `THREE.Timer`, and until then the honest thing is to
record it here rather than to filter it out of the console and call the console clean. Any gate that
asserts "no console errors" is unaffected: these are warnings.

**Also present under SwiftShader only.** `GL Driver Message (OpenGL, Performance, GL_CLOSE_PATH_NV,
High): GPU stall due to ReadPixels` — that is the e2e suite's own `getImageData` sampling, in
software rendering. It does not occur on a GPU and it is caused by the tests, not the app.

### Re-check before shipping

Three npm advisories were deferred pending Next 16.3 stable. **Re-run on 30 July 2026: still three,
still deferred, and here is the reason rather than the intention.**

`npm audit` reports three high-severity advisories, all transitive through `next` 16.2.12:

- **postcss ≤ 8.5.17** — XSS via an unescaped `</style>` in stringify output, and two
  `sourceMappingURL` path-traversal issues that disclose arbitrary `.map` files.
- **sharp < 0.35.0** — inherited libvips CVEs (2026-33327, -33328, -35590, -35591).

The advisory range for the fix is `next > 16.3.0-preview.7`, and **16.3.0 stable does not exist yet**:
the latest published stable is 16.2.12, which is what is installed. `npm audit fix --force` resolves
this by installing `next@9.3.3` — a downgrade of seven major versions that would take the App Router
with it. That is not a fix, so it is not taken.

Exposure, stated rather than assumed, because "high severity" is about the package and not about this
app. Both are build-time dependencies of a fully static export: `app/page.tsx` prerenders, the whole
site is `○ (Static)`, and there is no server route. postcss processes exactly one stylesheet,
`app/globals.css`, which this repo authors — there is no path by which an attacker supplies CSS or a
source map. sharp is Next's image optimiser, and this app ships no `next/image` and no remote images;
the only assets are the PNG renders in `design/`, which are never served. So the reachable attack
surface for all three is empty in this deployment, and the honest statement is that these are
upgrade debts to clear when 16.3 ships, not live vulnerabilities.

Re-check when 16.3.0 stable lands: `npm view next version`, then `npm i next@latest` and re-run the
whole gate set, because a Next major has already tilde-pinned React once in this project (R3F 9.6.1
declares `react: ">=19 <19.3"` while Next accepts `^19.0.0`).
