# P7 + P8 — walk it, then ship it

## P7 — first person and mobile

### Goal

Stand in the suite at eye height and walk it. Hand someone a phone and have it hold up.

### Why first person also fixes a debt

`stages.ts` carries a comment recording that the stage 4 → 5 camera path flies **through** the
partition between bedroom B and the hall, and at t = 0.7 landed half a foot from that wall — the
near plane — so every face clipped and the frame went empty. The workaround was to stay inside
bedroom B. Routing a path through the doorway needs a spline and collision, which is exactly what
first person builds. So P7 pays that back: once the walker exists, the threshold can land in the
hall, which was always the better shot.

### Contracts

```ts
// src/geo/walk.ts -- pure, no three.js
export const EYE = 5 + 10 / 12;      // 5 ft 10 in, already used by stages.ts
export const RADIUS = 0.75;          // shoulder half-width as a capsule
/** Slide along walls rather than stopping dead. Returns the resolved position. */
export function step(from: Vec2, to: Vec2, ctx: { walls: Wall[]; openings: Opening[] }): Vec2;
export function canPass(opening: Opening): boolean;   // doorway clearance vs RADIUS
```

```ts
// src/geo/route.ts -- pure
/** A walkable path between two rooms, through doorways, as waypoints. */
export function route(from: string, to: string, suite: Suite): Vec2[] | null;
```

`route()` is a graph search over `unreachableRooms()`'s adjacency, not a straight line. It returns
`null` when no doorway chain exists, which is the case `unreachableRooms()` exists to detect.

The capsule must not pass through a 0.5 ft partition at any step size. Test it at a deliberately
absurd step — a single frame of 40 ft/s at 5 fps is 8 ft, far more than a wall is thick — because
sweeping a point against a thin wall is the classic tunnelling bug and it only shows up on a slow
frame.

### Mobile

Touch orbit, a shortened intro, first person hidden (no pointer lock on touch), shadow map at 1024,
line widths reduced, DPR capped at 2. The HUD and panel are responsive at 375 / 768 / 1024 / 1440.

### Verification

`walk.spec.ts`: walk the hall end to end and assert the camera never leaves the suite footprint per
`collide.ts`; walk into every wall in turn and assert the position resolves to outside it; assert
the doorway is passable and a 0.5 ft gap is not.

`responsive.spec.ts` at all four widths: no horizontal scroll on `document.body`, every touch
target ≥ 44 × 44 CSS px, the HUD does not cover the viewport's centre.

### `A11yAlt.tsx`

A live region that describes, in prose, what the 3D view is currently showing: the stage, the room
the camera is in, its dimensions, and its provenance. A canvas is opaque to a screen reader, and the
`aria-label` currently on it is one sentence for the whole six-stage journey. The live region is the
non-visual equivalent of the model, and it is also the thing that makes the app usable with the
canvas failing to initialise at all — which is the honest fallback for a WebGL-less client.

Announcements must be throttled. A live region that fires on every frame is worse than none.

### Performance

`axe-core` zero violations on all six stages. Lighthouse ≥ 90 performance, 100 accessibility.
Code-split the globe so it leaves the critical path once you are past stage 0. Audit
`renderer.info` against the budget table in `docs/IMPLEMENTATION-PLAN.md` §9.

#### 1. The globe split: measured, and rejected

Built three ways and compared the emitted chunks. Next 16.2's Turbopack build **no longer prints a
size table at all**, with or without `--experimental-analyze`, so the bytes are the files under
`.next/static/chunks`. Byte-identical across two baseline builds, which is what makes the deltas
readable.

| build | scene chunk | delta | total JS |
|---|---|---|---|
| as shipped | 1,252,534 B | — | 1,885,152 B |
| `Globe` deleted outright | 1,251,818 B | **−716 B** | −716 B |
| `lazy(() => import("./Globe"))` | 1,252,102 B | **−432 B** | **+1,173 B** |

All four builds off one snapshot of the tree, which is what makes the deltas readable — the baseline
reproduced byte-identically twice, same chunk hash. The absolute figure moves with the tree and does
not matter to the comparison: the build at `d3036c0` reads 1,253,297 B.

The whole globe is **716 bytes of a 1.25 MB chunk — 0.06 %**, and under 1 kB of the 388 kB that
chunk transfers gzipped. It is three spheres and one import, and every three class it touches is
used elsewhere in the scene. The lazy boundary moves 432 of those bytes and ships **1,173 more in
total**, because it splits `geo/frames` into a 703 B chunk the main bundle still needs and still
fetches immediately (measured at +117 ms, alongside the main chunk), plus the globe's own 869 B.

And it breaks the descent, measured rather than feared, because **stage 0 is the globe and stage 0
is first paint** — "off the critical path" is a contradiction for this component. With the globe's
chunk delayed 2,500 ms and `journey.spec.ts`'s own frame metric sampled every 400 ms: **0.0 %
covered / 1 distinct colour from +850 ms to +2,905 ms**, then 45.2 % / 566 from +3,313 ms.
`journey.spec.ts`'s `nonBgPct > 8` fails on every frame in that window.

The R3F angle, also measured. R3F wraps `<Canvas>`'s children in a Suspense of its own whose
fallback is `<Block>`, which sets a never-resolving promise that `CanvasImpl` throws
(`if (block) throw block`). So **a suspending scene child suspends the canvas, not inside it** — up
to the nearest boundary outside, which is `CanvasHost.tsx`'s `loading`. Without an inner boundary the
served build showed the real UI at +461 ms, reverted to "LOADING WELD 15" — HUD, canvas and all — at
+763 ms, and came back at +3,189 ms. With `<Suspense fallback={null}>` inside, the canvas survives
and stage 0 is the empty void above instead. Both recorded in `CanvasHost.tsx`'s header, because the
next thing to reach for `useLoader` or `useGLTF` will hit it.

`experimental.optimizePackageImports` on `three-stdlib`, `@react-three/drei` and
`@react-three/postprocessing` was tried the same way and is also not taken: 1,252,534 → 1,250,403,
**2,131 bytes on 1.25 MB**. Turbopack was already tree-shaking those barrels.

#### 2. Frame time on real hardware

The number the project has never recorded. Two probes at each point: `window.__perf.medianMs`, which
`Perf.tsx` already publishes, and a `requestAnimationFrame` interval series for the p95 that
`__perf` does not carry — their medians agreed to within 0.2 ms everywhere, which is what makes the
second one trustworthy. **DPR 2**, which is what this display gives the app, **vsync off** so the
figure is the renderer's and not the panel's:

| sample | median | p95 | | sample | median | p95 |
|---|---|---|---|---|---|---|
| stage 0 | 2.6 ms | 3.1 ms | | stage 3, four cutaways | 2.5 ms | 3.6–3.7 ms |
| stage 1 | 2.7 ms | 3.2 ms | | stage 5 idle | 2.7 ms | 3.8 ms |
| stage 2 | 2.5 ms | 3.7 ms | | stage 5 walking (W held) | 2.8 ms | 4.0 ms |
| stage 3 | 2.6 ms | 3.8 ms | | stage 5 turning (A held) | 2.6 ms | 3.6 ms |
| stage 4 | 2.6 ms | 2.9 ms | | stage 0 revisited, warm | 2.6 ms | 3.0 ms |

At DPR 1 the same run reads **1.1–2.2 ms median, 2.9–4.1 ms p95**, 480–650 fps. So the app fits in a
16.7 ms budget four times over at 60 fps and twice over at 120, and `Perf.tsx`'s prediction of
"roughly 1-3 ms on a real GPU" was right to the millisecond. The headless figure this replaces is
62–79 ms, i.e. **software rendering is 25× the cost of the hardware here**, and every existing
draw-call gate exists because of that gap.

**Recorded, not gated**, per the standing rule. `perf.spec.ts` asserts only that the field is
populated.

Two caveats stated rather than buried. With **vsync on** the same runs read a flat **33.3 ms median
and 30.0 fps at every single sample point**, stage 4's 433 triangles included — a figure identical
across a 40-fold range of scene load is a cap, not a cost, so it is recorded as the cap it is. And
one early DPR 2 pass read stage 0 at median 5.9 / p95 31.9 ms; it did not reproduce in either of two
later runs (2.6 / 3.1 and 2.7 / 3.3) and is reported here as the outlier it was rather than dropped.

#### 3. Lighthouse

Lighthouse 13.4.1 against the production build on :3100, attached over CDP to the same headed Chrome
so the numbers are a real GPU's.

| preset | performance | accessibility | best practices | SEO |
|---|---|---|---|---|
| **desktop** | **81** | **100** | 96 | 100 |
| mobile (default) | 98 | 100 | — | — |

**Accessibility 100 on both, target met, zero failing audits.**

**Performance 81 on desktop, target missed, and the mobile 98 is not the app.** Take the mobile score
first, because it would be the flattering one to quote: at 412 × 823 `DesktopOnly.tsx` renders the
"open this on a laptop" message instead of the canvas, and the network log proves it — the 388 kB
scene chunk is **absent from the mobile run's 12 requests and present in the desktop run's 16**. The
mobile 98 is a score for a paragraph of text. The desktop 81 is the app.

Where the 19 points go, from the report rather than from a guess:

| audit | value | score |
|---|---|---|
| first contentful paint | 0.4 s | 1.00 |
| largest contentful paint | 0.9 s | 0.97 |
| speed index | 0.7 s | 1.00 |
| cumulative layout shift | 0 | 1.00 |
| **total blocking time** | **420 ms** | **0.39** |
| **max potential FID** | **320 ms** | **0.30** |
| unused JavaScript | 179 KiB | 0 |
| legacy JavaScript | 13 KiB | 0 |
| render-blocking requests | 3.7 kB of CSS | 0.50 |

TBT is the whole gap and TBT is three.js. Two long tasks, both attributed by Lighthouse to a file:
**322 ms evaluating the 388 kB scene chunk** and **202 ms evaluating react-dom's 64.5 kB**, against
645 ms of script evaluation in a 590 kB page. The 179 KiB of unused JavaScript is **154.9 kB (39.9 %)
of the scene chunk** and 28.8 kB (58.5 %) of Next's client runtime — that is three.js's unreached
code paths, which arrive whichever way the app imports it. The 13 KiB of legacy JavaScript is
`Array.prototype.at` / `.flat` polyfilling in Next's own 24 kB chunk, i.e. a browserslist target and
not our code.

So: **the performance target is missed by the cost of shipping a WebGL engine, and no
code-splitting in `src/scene` changes it** — the globe was 716 bytes and the barrel-import knob was
2,131. Two things could, neither of them a gate-tightening exercise: deferring the scene chunk past
first paint, which trades a real second of blank page for a metric, and dropping bloom, which is 17
of every frame's draw calls but not the main-thread cost. Both are decisions rather than fixes, and
they are handed over rather than taken. Interpreting rather than transcribing, as the brief asked:
FCP 0.4 s, LCP 0.9 s, CLS 0 and SI 0.7 s say the page paints and settles immediately; the sub-90
score is entirely one 322 ms parse-and-evaluate task, and this app's own frame time on the far side
of it is 2.6 ms.

### Console warnings, and which of them are ours

A clean console is part of shipping, so here is the accounting rather than a hope.

**Fixed.** `THREE.WebGLShadowMap: PCFSoftShadowMap has been deprecated` fired on every mount, six
times in an e2e run: `Experience.tsx` asked for `shadows="soft"` and three r183 deprecated that map
type. It now asks for `PCFShadowMap`, which is what three was substituting anyway — same rendering,
no warning.

**Not ours, and not fixable from here.** `THREE.Clock: This module has been deprecated. Please use
THREE.Timer instead` comes from `@react-three/fiber`'s own render loop —
`node_modules/@react-three/fiber/dist/events-*.esm.js` constructs a `Clock`, and so does
`three-stdlib`'s `EffectComposer`. Nothing in `src/` constructs one; checked by searching the whole
tree. It goes away when those packages move to `THREE.Timer`, and until then the honest thing is to
record it here rather than to filter it out of the console and call the console clean. Any gate that
asserts "no console errors" is unaffected: these are warnings.

**Also present under SwiftShader only.** `GL Driver Message (OpenGL, Performance, GL_CLOSE_PATH_NV,
High): GPU stall due to ReadPixels` — that is the e2e suite's own `getImageData` sampling, in
software rendering. It does not occur on a GPU and it is caused by the tests, not the app.

### Re-check before shipping

Three npm advisories were deferred pending Next 16.3 stable. **Re-run on 30 July 2026: still three,
still deferred, and here is the reason rather than the intention.**

`npm audit` reports three high-severity advisories, all transitive through `next` 16.2.12:

- **postcss ≤ 8.5.17** — XSS via an unescaped `</style>` in stringify output, and two
  `sourceMappingURL` path-traversal issues that disclose arbitrary `.map` files.
- **sharp < 0.35.0** — inherited libvips CVEs (2026-33327, -33328, -35590, -35591).

The advisory range for the fix is `next > 16.3.0-preview.7`, and **16.3.0 stable does not exist yet**:
the latest published stable is 16.2.12, which is what is installed. `npm audit fix --force` resolves
this by installing `next@9.3.3` — a downgrade of seven major versions that would take the App Router
with it. That is not a fix, so it is not taken.

Exposure, stated rather than assumed, because "high severity" is about the package and not about this
app. Both are build-time dependencies of a fully static export: `app/page.tsx` prerenders, the whole
site is `○ (Static)`, and there is no server route. postcss processes exactly one stylesheet,
`app/globals.css`, which this repo authors — there is no path by which an attacker supplies CSS or a
source map. sharp is Next's image optimiser, and this app ships no `next/image` and no remote images;
the only assets are the PNG renders in `design/`, which are never served. So the reachable attack
surface for all three is empty in this deployment, and the honest statement is that these are
upgrade debts to clear when 16.3 ships, not live vulnerabilities.

Re-check when 16.3.0 stable lands: `npm view next version`, then `npm i next@latest` and re-run the
whole gate set, because a Next major has already tilde-pinned React once in this project (R3F 9.6.1
declares `react: ">=19 <19.3"` while Next accepts `^19.0.0`).
