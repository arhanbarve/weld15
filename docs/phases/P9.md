# P9 — the descent becomes Earth

Status: **IMPLEMENTED on branch `p9-earth-descent`.** This document is the plan as written before
the work; §10 at the bottom records every place the implementation departed from it and why.
**Read §10 before trusting a number in §3, §5 or §6** — four of them are wrong and the corrections
are asserted in tests.

This document is written to be read by another agent with no memory of the conversation that
produced it. Everything load-bearing is either derived here or cited to a file and line. Where a
number was measured rather than chosen, the measurement is given. Where something is a judgement
call, it is labelled as one and the alternative it beat is recorded, because the next person to
read this will otherwise re-litigate it.

## 0. The complaint this answers

Two things, both correct, both observable in `design/renders/`:

1. **Stage 0 is a random sphere.** `src/scene/Globe.tsx` is 39 lines: one `sphereGeometry(1)` in
   flat `#0c3260`, a wireframe shell over it, one red dot at Weld's real latitude and longitude.
   There is no Earth in it. It is a grey-box that shipped in P2 and was never replaced.
2. **Stage 1 is an empty thing.** The stop is named "Cambridge". `src/data/campus.json` holds 36
   buildings whose total extent is 1,149 × 1,269 ft — Harvard Yard and nothing else. There is no
   city, no river, no terrain, no streets. The buildings float on a `gridHelper(3000)`.

The ask: make the descent read like Google Earth from orbit down to the point where the existing
design takes over.

### 2.3 Stage 0 is first paint, and a suspending scene child suspends the whole page

`src/scene/CanvasHost.tsx:15-31`, with a measurement behind it. R3F wraps `<Canvas>`'s children in

The file's own closing sentence: *"a scene child that can suspend — `useLoader`, a lazy component,
drei's `useGLTF` — needs its own Suspense inside `<Canvas>`, or the whole page blinks back to this

**P9b is exactly the thing that warning was written for.** See §6.5.

## 3. The mechanism

This section is the heart of the plan. Read it fully before touching any file. Everything in §5 and
§6 is an application of it.

### 3.1 Altitude is the parameter

Introduce one derived scalar, **nominal altitude in feet above Weld's grade**, written `alt`. It is
computed from the camera, not stored:

```
alt = camera.position.y        // three.js Y is up, and grade is y = 0
```

Every altitude-dependent behaviour in P9 — which ground quad is visible, the tint ramp, the label
set, the `--mass` opacity, near/far, and the globe's crossfade — is a pure function of `alt` and of
nothing else. This is deliberate and it is the property that makes the whole thing testable: a gate
can set a camera altitude and assert what should be on screen, without driving an animation.

**One module owns it.** New file `src/scene/altitude.ts`, three-free like `walk.ts` and `route.ts`,
holding the bands, the ramps and the near/far schedule as pure functions. Unit-testable without a
renderer. `tests/place.test.ts` already walks the real import graph to prove `walk.ts` and `route.ts`
are three-free; add `altitude.ts` to that assertion.

### 3.2 Where curvature stops mattering

Sagitta of a chord of length `L` on a sphere of radius `R`: `s = R - sqrt(R² - (L/2)²)`. Computed
for `R = 6,371 km`:

| ground extent in frame | sagitta | roughly, at 1080 px tall |
|---|---|---|
| 1,000 km | 19,650 m | tens of pixels |
| 100 km | 196 m | ~4 px |
| 50 km | 49 m | ~2 px |
| **25 km** | **12.3 m** | **< 1 px** |
| 5 km | 0.5 m | negligible |

At 45° vertical fov the frame covers `0.828 × alt` of ground. Sub-pixel curvature at 25 km of
extent therefore corresponds to **`alt` ≈ 30 km ≈ 99,000 ft**.

So: above ~99,000 ft the Earth must be a sphere. Below it, a flat plane is correct to within a
pixel. That is the whole argument for where the swap goes, and it is a computation rather than a
taste.

### 3.3 The globe is a depth-less backdrop, and that is what dodges the precision problem

This is the key design move. Three properties, together:

1. **The globe mesh is drawn at a proxy scale, with the camera-to-centre distance scaled to match.**
   Perspective projection is invariant under a uniform scaling of the whole scene about the camera,
   so scaling both the sphere radius and the camera-to-centre distance by the same factor produces a
   **pixel-identical** image. To depict altitude `alt`:

   ```
   GLOBE_R          = far(alt) / 8                          // NOT a constant. See below.
   distanceToCentre = GLOBE_R * (1 + alt / R_EARTH_FT)      // R_EARTH_FT = 20,902,231
   cameraToSurface  = GLOBE_R * alt / R_EARTH_FT
   ```

   **`GLOBE_R` is tied to `far`, and that is not decoration — a fixed radius does not work.** The
   first draft of this plan used a constant `GLOBE_R = 5000` ft and it is wrong: at the top of the
   swap band (`alt` = 99,000 ft) that puts the globe's surface 23.7 ft from the camera against a
   near plane of 100 ft, so the sphere is clipped away entirely at exactly the altitude it still has
   to be visible. Computed against the §3.4 schedule:

   | `alt` | near | far | `GLOBE_R` | camera-to-surface | back of globe |
   |---|---|---|---|---|---|
   | 3.344e7 (stage 0) | 100 | 4,000,000 | 500,000 | 799,915 ✓ | 1,799,915 ✓ |
   | 99,000 | 100 | 4,000,000 | 500,000 | 2,368 ✓ | 1,002,368 ✓ |
   | 60,000 | 62 | 2,481,569 | 310,196 | 890 ✓ | 621,283 ✓ |
   | 40,000 | 42 | 1,685,985 | 210,748 | 403 ✓ | 421,900 ✓ |
   | 20,000 | 22 | 843,793 | 105,474 | 101 ✓ | 211,049 ✓ |
   | **4,180** | 5.0 | 163,932 | 20,492 | **4.1 ✗ clipped** | 40,987 ✓ |

   The rule holds while `alt > 8 / (far/near) × R_EARTH_FT`, which at the schedule's ratio of ~4e4 is
   **`alt` > 4,180 ft**. The globe's fade completes at 40,000 ft (§3.7), so there is a **9.6×
   margin** and the globe is fully transparent long before the rule expires. `globeRig.ts` must
   nonetheless assert this precondition rather than trust the band table, because the two are
   maintained separately.

2. **It renders with `depthTest: false`, `depthWrite: false`, `renderOrder: -1`.** It is a backdrop,
   not a participant. Nothing in the scene ever needs to depth-composite against it, because by the
   altitude at which anything else is on screen, the sphere is flat to within a pixel behind it.

3. **Therefore near and far never have to span both scales.** They only ever have to serve the
   foot-scale content. There is no logarithmic depth buffer, no relative-to-eye rendering, and no
   interaction with the existing `EffectComposer` in `src/scene/Effects.tsx`.

This third point is the payoff. The research on real globe renderers correctly identifies log depth
and origin-recentring as the standard fixes for a camera 6,371 km from a sphere-centred origin. **We
never create that situation.** The origin stays at Weld's centroid, exactly where `frames.ts` puts
it, and the sphere is a proxy at a convenient scale. Nothing in `src/geo/` changes.

> If an implementer finds themselves adding `logarithmicDepthBuffer: true` to the `<Canvas>` in
> `Experience.tsx`, they have departed from this plan and should stop and re-read this section.

### 3.4 Near and far become functions of altitude

`Experience.tsx:98` currently hard-codes `near: 0.5, far: 25_000`. Under P9 those become a schedule
in `altitude.ts`, applied by `CameraRig` in the same place it already writes `camera.fov` and calls
`updateProjectionMatrix()`.

Constraints the schedule must satisfy:

- `near` must stay at **0.5** for stages 4 and 5. `stages.ts:161-177` records the measured defect
  that made 0.5 load-bearing: at `hallWidth = 3`, which is the low end of a shipped slider, the old
  straight blend passed 0.40 ft from a wall band and every face clipped. Do not touch it.
- `far` at stage 3 is 25,000 ft today, which already clips well before the 20.7 km horizon. Keeping
  `far` modest and fading the ground to the background colour is how the outer quad's edge is never
  seen. See §3.6.
- The ratio `far / near` should stay under roughly 1e5 to keep 24-bit depth well conditioned.

Proposed schedule, to be pinned by unit test rather than tuned by eye:

| `alt` | near | far | ratio |
|---|---|---|---|
| ≤ 200 ft | 0.5 | 25,000 | 5e4 |
| 1,600 ft | 2 | 60,000 | 3e4 |
| 28,000 ft | 30 | 1,200,000 | 4e4 |
| ≥ 99,000 ft | 100 | 4,000,000 | 4e4 |

Interpolated logarithmically in `alt` between the rows. The values must be **monotonic** in `alt`
and must never move during a single stage's dwell, or the depth buffer resolution changes under a
static shot and z-fighting appears and disappears.

### 3.5 The nested ground quads

The ground is not one plane. It is four concentric axis-aligned quads in the site frame, centred on
Weld's centroid, drawn outermost-first:

| quad | extent | texture | source resolution | ft per texel |
|---|---|---|---|---|
| Q1 | 3,280,000 ft (1,000 km) | L1 | 2048 × 1524 | 1,602 |
| Q2 | 164,000 ft (50 km) | L2 | 2048² | 80.1 |
| Q3 | 16,400 ft (5 km) | L3 | 2048² | 8.0 |
| Q4 | 1,600 ft (488 m) | L4 | 3333² | **0.480** |

Each is 10× the last, which means each is a factor of 10 sharper over its own footprint. Inner
quads are drawn last with `depthWrite: false` and ascending `renderOrder`, so they simply paint over
the outer ones — no z-fighting, no polygon offset, no depth participation at all. Two triangles
each, so four quads is four draw calls.

**Q1 is flat where the Earth is not, and the horizon fade is what covers that.** At 1,000 km of
extent the sagitta is 19,650 m — tens of pixels, not sub-pixel. Q1 is only ever on screen between
400,000 ft and 40,000 ft of altitude, where the globe is still drawn behind it at partial opacity
and where everything past ~150 km is inside the fade of §3.6. **Verify this at the stage-1 tilt
before accepting it**: if the flat far field reads as wrong at 28,000 ft, the answer is to bring the
fade in closer, not to subdivide Q1.

**Q4 is at the source's native resolution and cannot be improved.** MassGIS 2025 is 15 cm, which is
0.492 ft per pixel; Q4 at 3333 px over 1,600 ft is 0.480 ft per texel. Stage 3 wants
`208 ft / 720 px = 0.289 ft per screen pixel`. So the deepest imagery is about 1.7× softer than the
stage-3 frame demands. **This is a floor set by the best legally redistributable imagery that
exists for this location, not a budget choice**, and the doc says so rather than letting a later
reader think it was laziness. It is also largely hidden: at stage 3 the massing covers every
building footprint (§6.9) and what remains photographic is grass and paving, which tolerate softness.

### 3.6 The horizon fade

A flat quad has an edge, and at any oblique angle a viewer sees it. Every flight simulator solves
this the same way and so does P9: the ground quads fade to the scene background colour with radial
distance, over the outer 20% of each quad's extent. Implemented as a `onBeforeCompile` patch or a
small custom `ShaderMaterial`, not as fog — `THREE.Fog` is scene-global and would also fog the
suite's interior at stage 5.

At stage 3 the far plane is 25,000 ft and the horizon is 67,812 ft away, so the fade and the far
plane agree: the ground is gone before it curves.

### 3.7 The bands, end to end

| `alt` | globe | Q1 | Q2 | Q3 | Q4 | massing | tint |
|---|---|---|---|---|---|---|---|
| ≥ 3.3e7 ft (stage 0) | 1.0 | — | — | — | — | — | full colour |
| 3.3e7 → 400,000 | 1.0 | — | — | — | — | — | full colour |
| 400,000 → 99,000 | 1.0 | fade in | — | — | — | — | full colour |
| 99,000 → 40,000 | fade out | 1.0 | fade in | — | — | — | full colour |
| 40,000 → 4,000 | — | 1.0 | 1.0 | fade in | — | fade in | begins |
| 4,000 → 400 | — | — | 1.0 | 1.0 | fade in | 1.0 | ramping |
| ≤ 400 (stage 3) | — | — | 1.0 | 1.0 | 1.0 | 1.0 | full |

Every fade is one octave of altitude wide, cross-dissolved. No band boundary coincides with a stage
boundary, deliberately: a transition that happens exactly when a stage changes is a transition
nobody can tell from a cut.

## 5. P9a — the flight

**Ships a continuous, correct, gate-able descent with no imagery whatsoever.** The globe stays the
flat blue sphere it is today; only its geometry, lighting and rig change. This is deliberate: the
hard camera-and-scale work gets verified against a texture-free build, so that if a fade looks wrong
in P9b it is the imagery and not the flight.

### 5.1 Re-pitched stops

Derived, not chosen. At 45° vfov, `distance = frameHeight / (2 tan 22.5°) = frameHeight / 0.8284`.

- **Stage 1** must frame Cambridge, ~23,000 ft across → **27,763 ft**. Round to a pose at
  `alt ≈ 28,000 ft`.
- **Stage 2** must frame the full `campus.json` extent of 1,269 ft plus margin, say 1,300 ft →
  **1,569 ft**. Round to a pose at `alt ≈ 1,570 ft`.

Both must be written as **derivations in code**, in the manner `stages.ts:136-137` already writes
`gableBack` as a function of `GABLE_FOV` — the comment there records that a hard-coded 40 ft
survived a change of fov and quietly stopped framing the building. Do not repeat that.

**kf0 changes units, which is not the same as changing framing.** Today `kf[0]` is
`{ position: [0, 0, 2.6] }` in the globe's own unit scale (`stages.ts:216`). Under §3.1 there is one
frame and `alt = camera.position.y`, so kf0 becomes a foot-scale pose at
`alt = 1.6 × R_EARTH_FT = 33,443,570 ft`, looking down Weld's local vertical. The **image** at stage 0
is unchanged — the globe proxy reproduces it exactly, which is what §3.3's invariance argument buys
— but every number in that keyframe is different, and `tests/stages.test.ts` asserts on kf0. Expect
that edit and make it deliberately.

Stage 3 does **not** move. `STAGE3_CLAMP` derives `minRadius` from
`MASS_RADIUS = hypot(footprintRadius, 85.4) = 114.9 ft` (`orbit.ts:68,95`), and `orbit.ts:71-93`
derives the whole clamp from it. Moving stage 3 invalidates that derivation.

**Tilt.** Stage 1's new pose should look down at roughly 35–45° from nadir rather than the current
near-45° oblique, so the horizon is out of frame at 28,000 ft where it is 330 km away. Stage 2 keeps
a similar tilt. Exact angles are a framing judgement; whatever is chosen must be recorded with the
reason, and the horizon fade (§3.6) must be verified to hide the quad edge at that angle.

### 5.2 Paths on stages 0–2

`Keyframe.path?: PathStop[]` already exists (`stages.ts:31-38`) and `alongPath()` and `blend()`
(`:320-355`) already walk it. **Neither function changes.** `cameraKeyframe()` (`:426-436`) currently
special-cases `stage !== 4`; it becomes generic:

```ts
export function cameraKeyframe(kf, stage, t, reduced) {
  const path = kf[stage].path;
  if (!path) return kf[stage];
  if (reduced) return t < REDUCED_CUT ? path[0].frame : path[path.length - 1].frame;
  return alongPath(path, t);
}
```

That is strictly more general than what is there and preserves stage 4's behaviour exactly, because
stage 4 has a path and stages 3 and 5 do not.

Waypoints for each stage's path are chosen so the flight is a **descent along Weld's local
vertical**, the way a Google Earth "fly to" arrives: the camera rotates so Weld comes to frame
centre while still high, then descends. Each stop's path ends at the next stop's keyframe **object,
not a copy of its numbers** — `thresholdPath()` at `stages.ts:288-296` already does this and
explains why: so `cameraKeyframe(kf, n, 1)` and `kf[n+1]` are the same pose exactly and the stage
boundary cannot show a jump of a thousandth of a foot.

### 5.3 The true subsolar point

`src/geo/solar.ts` already exports `solarDeclinationDeg()` (`:98`) and computes `equationOfTimeMin()`
privately (`:112`). The subsolar point is:

```
lat = solarDeclinationDeg(date)
lon = -15 * (utcHours + equationOfTimeMin(date)/60 - 12)
```

Add `subsolarPoint(date): { lat, lon }` to `solar.ts` and test it against two known instants, in the
manner the module header already describes for its other identities. `Lighting.tsx`'s
`cambridgeInstant(date, hour)` (`:189`) already converts the store's wall clock to the instant
`solar.ts` wants, so the globe's sun and the building's sun come from **one** conversion. That is the
point: moving the existing hour slider at stage 0 sweeps real daylight across the real Earth, and
Weld's marker is truthfully in day or in night.

### 5.4 The globe itself

- Sphere at `GLOBE_R = 5000` ft, `depthTest: false`, `depthWrite: false`, `renderOrder: -1`.

### 6.3 `scripts/fetch-imagery.mjs`

The script is the provenance. It must be readable as a record of exactly what produced each file.

**Steps, in order:**

1. Download each source to a git-ignored cache directory. Record URL, HTTP date, and SHA-256 of
   every download in the manifest.
2. **Reproject into the project's own frame.** This is the step most likely to be got wrong.
   - MassGIS is EPSG:6348, NAD83(2011) UTM zone 19N. `frames.ts:38-45` uses an equirectangular
     approximation about Weld's origin with `x` east and `y` north in feet.
   - **UTM grid north is not true north.** Convergence `γ = (λ − λ₀)·sin φ`, with `λ₀ = −69°` for
     zone 19N: at Weld, `γ = (−71.1171195 + 69) × sin(42.3739244°) = **−1.4269°**`. Over the Yard's
     1,269 ft extent that is **31.6 ft** of corner-to-corner misalignment against `campus.json`.
   - **Every MassGIS-derived level must be rotated by +1.4269° about Weld's origin during
     resampling**, so that the imagery's north is true north and the quads are axis-aligned in the
     site frame. Getting this wrong rotates the entire photographed Yard against the modelled one.
     It is precisely the class of silent error `frames.ts:13-17` warns about: *"A mistake in that
     swap mirrors the entire building, and mirroring is already a live ambiguity in this project, so
     a silent mirror would be invisible."*
   - Verification: after resampling, project three `campus.json` building corners through
     `latLonToSite()` and confirm they land on the corresponding rooftops in the L4 image, to within
     a few feet. **Do this by eye on an overlay and commit the overlay to `design/renders/`.** A
     1.4° rotation is invisible in a number and obvious in a picture.
3. **Composite L2 over an ocean base.** Measured: MassGIS coverage stops at the state boundary, so a
   50 km frame centred on Cambridge has **black no-data holes over Massachusetts Bay and a white
   wedge offshore**. Composite the MassGIS layer over an upsampled BMNG crop of the same extent, so
   no-data areas receive Blue Marble's ocean. L3 and L4 are clean and need no compositing.
4. Encode to AVIF q55 and WebP q80 at the dimensions in §6.2.
5. Emit `public/imagery/manifest.json`: for each level, the file names, pixel dimensions, the
   geographic extent **expressed in site feet** (`minX, maxX, minY, maxY`), the source dataset, the
   capture date, the licence, the attribution string, and the source SHA-256.

`imagery.ts` reads the manifest and derives the quad extents from it. **The quad sizes in §3.5 are
not hard-coded in the scene**; they come from the manifest, so an imagery change cannot silently
disagree with the geometry.

### 6.4 Loading, and the trap it must avoid

Re-read §2.3. **Do not use `useLoader`, `useTexture`, or `useGLTF` anywhere in the scene graph.**

The loader is imperative:

```ts
// sketch, not final
const [tex, setTex] = useState<THREE.Texture | null>(null);
useEffect(() => {
  let live = true;
  new THREE.TextureLoader().load(url, (t) => { if (live) { t.colorSpace = THREE.SRGBColorSpace; setTex(t); } });
  return () => { live = false; };
}, [url]);
```

A quad with no texture yet renders nothing at all — not a placeholder, not a suspense boundary,
nothing. The band table in §3.7 guarantees that at every altitude at least one layer is already
loaded, and the 512 × 256 Earth thumbnail is imported into the bundle so stage 0 has a texture on
the very first frame.

Prefetch one level ahead of the camera's current band. Fade each level in over ~250 ms when it
arrives, on `MASTER.md:89`'s micro-interaction timing.

**Add an e2e gate that the "LOADING WELD 15" fallback never reappears after first paint.** That is
the exact failure P8 measured and the reason this section exists.

## 10. What the implementation changed, and why

Written after the fact. Every item here is a place the plan above is WRONG or was improved on; each
correction is asserted by a test rather than left as prose. Where the plan is right, it is not
mentioned.

### 10.1 The globe-clip floor is 4,973 ft, not 4,180 (§3.3)

§3.3 derives the altitude below which the proxy sphere is clipped by the near plane as
`alt > 8 × R_EARTH / (far/near)`, substitutes "the schedule's ratio of ~4e4", and gets 4,180 ft.
**The ratio is not constant.** At that altitude it is 33,622, and the condition is a **fixed point**
— the altitude at which the rule expires depends on the near and far planes at that same altitude —
so it has to be solved, not substituted. `altitude.ts globeClipFloor()` solves it by iteration:
**4,973 ft**. The margin against the globe's fade-out at 40,000 ft is therefore **8.0×**, not the
9.6× §3.3 claims. Still ample. `tests/altitude.test.ts` asserts the floor, that it really is the
fixed point, and that the constant-radius version fails — so the test is not a tautology.

### 10.2 §5.1's stop altitudes do not compose with its own tilts

§5.1 computes stage 1 at 27,763 ft and stage 2 at 1,569 ft from `distance = frameHeight / 0.8284`,
which is a **nadir** framing formula, and then §5.1's "Tilt" paragraph asks for 40°. The two do not
compose: an oblique camera sees ground extent `2·drop·tan(fov/2) / cos²(tilt)`, so it sees **more**
ground than a nadir camera at the same height. Framing Cambridge from 28,000 ft at 40° puts
39,528 ft in the frame, not 23,000.

`stages.ts obliqueDrop()` derives the altitudes correctly. Shipped: **stage 1 at alt 16,332 ft**
(tilt 40°, frames 23,000 ft) and **stage 2 at alt 815 ft** (tilt 45°, frames 1,300 ft). The horizon
is out of frame at both — top edge at 62.5° and 67.5° from nadir.

### 10.3 kf0 is at 1.5 Earth radii, not 1.6 (§5.1)

The globe's disc is centred on the direction to Earth's **centre** while the camera aims at **Weld**,
and those differ. Tilting by τ moves the disc off frame centre by `τ − atan(alt·tanτ/(alt+R))`.
Measured:

| alt | disc half-angle | overfill vs 22.5° | tilt 0.3° | tilt 1° | tilt 2° | tilt 3° |
|---|---|---|---|---|---|---|
| 1.6 R | 22.6199° | 0.12° | holds (0.005 to spare) | **void band** | **void band** | **void band** |
| 1.5 R | 23.5782° | 1.08° | holds | holds | holds (0.28 to spare) | **void band** |

At 1.6 R any tilt past 0.3° opens a band of empty background along the bottom of the first frame the
viewer ever sees. 0.3° was rejected as too close to the straight-down singularity in `lookAt` to be
relying on a library's degeneracy guard for the camera's roll — and the roll is what puts north up.
So kf0 is **1.5 R (31,353,347 ft) at 2° of tilt**.

### 10.4 The imagery comes from the tile service, not the JP2 orthos (§6.1, §6.3)

**This removes the phase's highest-likelihood risk rather than mitigating it.** §6.3 requires every
MassGIS-derived level to be rotated by +1.4269° because UTM 19N grid north is not true north — 31.6 ft
of corner-to-corner misalignment across the Yard if missed or mis-signed, and §7 rates it high
likelihood and invisible in code.

`scripts/fetch-imagery.mjs` uses MassGIS's cached tile service, which serves the same imagery in
**EPSG:3857**. Web Mercator is normal-aspect cylindrical, so meridians are vertical and the
convergence term is **identically zero**. The rotation does not exist. Verified on a committed
overlay: `design/renders/p9-georef-overlay.png` and `p9-georef-weld.png` draw all 36 `campus.json`
footprints and `weld.json` onto the deepest plate — every outline on its roof, Weld on Weld, and no
rotation of the set.

Costs, stated rather than glossed: 8-bit RGB rather than the 4-band originals (nothing wants NIR); a
resampled pyramid, so z20's 0.362 ft grid is **finer than the 0.492 ft the imagery was flown at** and
the manifest records the native figure as the resolution and the grid separately; z21 is 404, so z20
is the floor. Licence identical either way.

### 10.5 The pyramid as actually built (§6.2)

| level | extent | px | AVIF | WebP | source |
|---|---|---|---|---|---|
| L0 | whole Earth | 4096 × 2048 | 439 KB | 560 KB | BMNG August 2004 |
| L1 | 1,000 km | 2048 × 1524 | 55 KB | 69 KB | BMNG crop |
| L2 | 50 km | 2048² | 545 KB | 910 KB | MassGIS z13 over BMNG ocean |
| L3 | 5 km | 2048² | 590 KB | 1,056 KB | MassGIS z16 |
| L4 | 1,600 ft | 3072² | 625 KB | 947 KB | MassGIS z20, 0.52 ft/texel |

**2.20 MB AVIF** (under §6.2's 2.6 MB estimate) and **5.66 MB with WebP** (over its 4.1 MB, because
WebP is 2.6× AVIF on photographic content rather than the 1.5× assumed). All 225 + 156 + 361 tiles
had coverage, so L2's ocean composite found no no-data to fill at this extent; the step is kept
because it is correct at any extent.

The manifest lives in `src/data/`, not `public/` — **imported, not fetched**, so `MASTER.md:80`'s
offline claim survives and no network request sits on the critical path before ground can be drawn.

### 10.6 The horizon fade is 0.28 of the half-extent, not 0.20 (§3.5)

Taking §3.5's own instruction ("bring the fade in closer, not subdivide Q1") rather than overriding
it. Applied to every quad so there is one number instead of four. The falloff is **Chebyshev** —
`max(|u|,|v|)`, not `length(uv)` — so it follows the quad's square boundary; a circular falloff
leaves the four corners fully opaque, which is exactly the edge the fade exists to hide.

### 10.7 The tint stops at 0.82, saturation at 0.25 (§6.5)

Not 1.0. A fully tinted photograph is a flat blue rectangle with every bit of tonal information
gone, and what stage 3 wants is a photograph that has become *the ground the drawing sits on*. The
18% that survives keeps the paths across the Yard readable under the cyanotype. Both numbers, and the
40,000 → 400 ft ramp bounds, are design-system tokens in `MASTER.md` per §6.6.

### 10.8 Four defects found by looking, not by testing

Recorded because each was invisible to tsc and to the unit suite:

1. **The terminator was mirrored.** `DirectionalLight` aims at `light.target`, which defaults to an
   `Object3D` at the **world** origin — Weld's centroid, tens of millions of feet from the proxy's
   centre. Lights are also scene-global rather than scoped to their group, so it lit Campus too. The
   sun is now a normalised site-frame direction in a uniform.
2. **Weld's marker was invisible.** It was opaque while the sphere was transparent, and three renders
   the opaque queue before the transparent one **regardless of `renderOrder`**, so the sphere painted
   over it every frame.
3. **The atmosphere was a flat wash, not a rim.** "BackSide + additive gives fresnel for free" is
   false — a `MeshBasicMaterial`'s opacity is constant over the surface. It is a real shader now.
4. **Mutating a memoised `uniforms` object does nothing.** The object the material ends up holding is
   not the one passed to `<shaderMaterial uniforms={...}>`, so the write lands on a copy and the
   sampler stays unbound. **No error is raised** — an unbound `sampler2D` is simply not drawn — so
   all four ground quads rendered at the right size, in the right place, visible, in frustum, and
   completely blank. Both `Ground.tsx` and `Globe.tsx` now bind through the material ref inside
   `useFrame`.

### 10.10 A trap in the test harness, worth more than the phase that found it

`playwright.config.ts` sets `baseURL` to `localhost:3000` with `reuseExistingServer: true`. **If any
dev server is already listening there — including one from a different worktree or the main checkout
— Playwright adopts it and says nothing.** The first full P9 e2e run reported **46 passed while
testing code with none of P9 in it.** The give-away was that `/imagery/l4.avif` returned 404 on 3000
and 200 on the worktree's own server, and that the campus report showed 22 draw calls where the
worktree measures 24. Pointed at the right server the same suite reported 4 failed.

The flag is left true — for a single checkout it is correct, and disabling it makes every local run
pay a cold Next start — but the hazard is now documented in the config. **Before trusting a green run
from a worktree, request a file only your branch has.**

### 10.12 The last three items, and what each turned up

All three are now done. Each surfaced something the plan had not anticipated.

**`Labels.tsx`** (§6.7) — five places, North America down to Harvard Yard, each on a real
lat/lon through `latLonToSite()` so the label lands on the thing it names. Weld Hall is
deliberately **not** in the table: `Campus.tsx` already mounts that chip tied to `highlightWeld`,
and a second would double-label it.

Two departures from the pattern §6.7 prescribes. It says to reuse `Campus.tsx`'s `<Html>` approach,
and the CSS is reused — but **not `distanceFactor`**. Scaling with scene distance is right for a
label pinned to a building you are approaching and wrong for one pinned to a continent: across eight
million feet to two hundred, a scaled chip is either a smear or a single pixel. And **"Harvard Yard"
had to move off Weld.** Placed at Weld's own coordinates its chip landed exactly on top of the
"Weld Hall" chip — two overlapping labels on one building, which is worse than neither. It now sits
450 ft west and 320 ft north, on the grass of the Old Yard, which is what the name actually means.
`tests/e2e/imagery.spec.ts` asserts the two boxes do not intersect.

**The `--mass` altitude ramp** (§6.9) — `massOpacity(alt, highContrast)` in `Campus.tsx`, ramping
0.10 → 0.34 across the massing band, ×2.2 in high contrast per `MASTER.md`'s own token pair.

**§6.9 asked for full occlusion of the photographed roof and that is not achievable.** Measured at
stage 2, luminance standard deviation over an 80 × 60 patch:

| patch | sd | mean |
|---|---|---|
| open ground, no building | 29.51 | 91.6 |
| a roof under the old flat 0.12 of mass | 28.88 | 100.1 |

Two per cent of the photograph's texture removed — so each footprint was marked by its edges alone
and the roof inside it was still the photograph, which is the doubled image decision 9 wanted gone.
But blending is linear, so residual texture is `(1 − α)` × the photograph's, and getting sd under 6
needs **α > 0.81**. A campus at 0.81 is not a cyanotype; it is solid blue blocks, and translucent
mass over line work is the whole SCAN palette. `MASTER.md`'s token is 0.10. So the ceiling is a
deliberate partial at 0.34 — a quarter of the residual texture removed, enough that a footprint
reads as occupied — and `tests/labels.test.ts` asserts `MASS_MAX < 0.5` as a guard rail so a later
attempt to "finish" the occlusion fails a test rather than quietly changing the look.

Weld's pulse became a **multiplier** on the ramp rather than an absolute 0.2–0.34 range: once the
rest of the campus reaches 0.34, an absolute pulse at 0.34 would make the highlighted building
identical to its neighbours at exactly the stage it most needs to stand out.

**`tests/e2e/imagery.spec.ts`** (§4, §6.4) — four tests. The load-fallback gate uses a
`MutationObserver` installed before the canvas exists rather than sampling, because the failure is
transient by nature: P8's measurement had the page away for 2.4 s and back, and a screenshot either
side of that shows nothing wrong. It counts sightings before first paint (legitimate) and asserts
none after.

One assertion in that file was **written, found to be wrong, and removed**. It measured mean frame
chroma and expected it to fall as the tint rose. Measured: 4.4 at stage 1, **18.9** at stage 2 — it
rises, because the metric is confounded by content, not because the tint is broken. At 16,332 ft the
frame is the 50 km plate at 80 ft/texel, uniformly grey greater-Boston at a grazing angle; at 815 ft
it is the 0.52 ft plate plus blue massing, white edges and a crimson chip. The tint is a 19% effect
at the first and 85% at the second and is swamped both times. The ramp is a pure function of
altitude and is asserted in `tests/altitude.test.ts`, which is the right level for it.

### 10.13 The AVIF false negative, fixed

§10.11 recorded that `pickFormat()` tested AVIF **encode** support via `canvas.toDataURL`, which
Chrome lacks — it returns a PNG data URL — while Chrome decodes AVIF perfectly well. So every Chrome
user was served the WebP plates: **2.98 MB instead of 1.76 MB**, for a capability they had. A false
negative, and an invisible one, because the wrong answer still works.

There is no reliable synchronous test for decode support, so the capability test is gone.
`levelUrls()` returns AVIF then WebP, and `loadTexture()` walks the list, falling through on a decode
failure — which is what a `<picture>` element does, and is correct by construction rather than by a
table of browser behaviour. The cost of being wrong is one failed request on a browser without AVIF,
against 1.2 MB saved on every browser with it.
